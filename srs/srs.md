## 1. Введение {#1-introduction}

Настоящий документ представляет собой спецификацию требований к программному обеспечению (SRS) для клиентского веб-приложения «EventPass — приложение посетителя». Документ задает перечень функциональных возможностей, интерфейсных решений, качественных характеристик обслуживания и ограничений проектирования, необходимых для реализации и последующего приемочного тестирования подсистемы.

### 1.1 Назначение документа {#11-document-purpose}

Настоящая спецификация предназначена для фиксации полного набора требований к продукту «EventPass — приложение посетителя» и служит формальным соглашением между Заказчиком и проектной командой. Документ адресован разработчикам клиентской части, инженерам тестирования (QA), архитекторам интеграционных решений и преподавателю, контролирующему соответствие жизненному циклу разработки ПО. Спецификация определяет, **что** приложение обязано выполнять в рамках бизнес-сценариев, не ограничивая внутреннюю архитектуру программной реализации.

### 1.2 Область применения продукта {#12-product-scope}

Продукт «EventPass — приложение посетителя» (версия 1.0) представляет собой клиентское веб-приложение для взаимодействия посетителей мероприятий с билетной платформой. Приложение решает задачи поиска событий, фильтрации по критериям, резервирования мест, оформления покупок и предоставления динамического электронного билета с QR-кодом для прохождения валидации на пунктах контроля доступа.

* **Входит в границы продукта:**
  * Просмотр каталога мероприятий с постраничной пагинацией и мультикатегорийной фильтрацией.
  * Просмотр детальной карточки мероприятия с актуальными квотами свободных мест.
  * Корзина с возможностью выбора билетов (включая тарифы «Стандарт» и «VIP») и таймером резервирования мест на 15 минут.
  * Оформление покупки (в учебном режиме с эмуляцией платежного шлюза).
  * Экран визуализации билета с высококонтрастным QR-кодом для оптического сканирования.
  * Личный кабинет со списком завершенных заказов и статусами билетов («Действителен», «Использован», «Возвращён»).
* **НЕ входит в границы продукта:**
  * Административная панель организатора для создания событий и просмотра аналитики продаж (компонент № 1).
  * Серверный модуль сканирования и live-график заполняемости турникетов (компонент № 4).
  * Реальная интеграция с банками и платежными шлюзами эквайринга (используется имитация успешной транзакции).
  * Нативные мобильные клиенты под iOS и Android (разработка ведется как Mobile-first Web-приложение).

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

Приложение «EventPass» выступает клиентским веб-фронтендом модульной системы распространения билетов. Продукт взаимодействует со следующими компонентами платформы:
* **Сервис билетов (Компонент № 2):** предоставляет REST API для каталога, резервирования мест, генерации QR-кодов и фоновой отправки копий билетов через Mock SMTP.
* **Сервис аутентификации:** обеспечивает безопасный выпуск, валидацию и отзыв сессионных JWT-токенов.
* **Сервис валидации доступа (Компонент № 4):** внешняя подсистема контролеров, оптически считывающая экран с QR-кодом, отображаемым в приложении посетителя.

### 2.2 Функции продукта {#22-product-functions}

* Аутентификация и регистрация посетителей по связке email и пароля.
* Отображение адаптивного каталога мероприятий с постраничной навигацией.
* Поиск по названию и многопараметрическая фильтрация (город, дата, категория, диапазон цен, типы мест).
* Просмотр карточки мероприятия с детальной программой, местом проведения и оставшимися квотами билетов.
* Управление корзиной билетов с блокировкой мест на сервере и отображением таймера бронирования.
* Оформление заказа с подтверждением и генерацией электронного билета.
* Отображение полноэкранного билета с высококонтрастным QR-кодом.
* Просмотр истории покупок с детализацией статусов заказов и выгрузкой билетов.

### 2.3 Ограничения продукта {#23-product-constraints}

* **CON-01 (Платформа):** Приложение должно функционировать во всех современных веб-браузерах (Google Chrome, Mozilla Firefox, Safari, Microsoft Edge) без использования сторонних расширений.
* **CON-02 (Адаптивность):** Интерфейс должен строиться по концепции Mobile-first и сохранять полную функциональность при ширине экрана от 360 px до 1920 px.
* **CON-03 (Оплата):** В рамках текущей версии платежные транзакции не связываются с реальными банковскими процессингами и эмулируются на программном уровне.
* **CON-04 (Правовое регулирование):** Хранение и передача персональных данных должны строго отвечать требованиям Закона РБ № 99-З «О защите персональных данных».

### 2.4 Характеристики пользователей {#24-user-characteristics}

* **Гость (неавторизованный пользователь):** Физическое лицо, просматривающее каталог и карточки событий. Специальных технических навыков не требуется.
* **Авторизованный покупатель:** Пользователь, прошедший вход в систему. Обладает правами резервирования билетов, оформления заказов, доступа к экрану QR-кода и архиву заказов.
* **Служба технической поддержки:** Персонал, обрабатывающий спорные ситуации по заказам через идентификаторы транзакций.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

* Предполагается постоянная доступность серверного REST API (компонент № 2) с форматом обмена данными JSON.
* Устройство пользователя оснащено исправным экраном с достаточным запасом яркости для уверенного распознавания QR-кодов оптическими сканерами турникетов.
* Сбои или задержки почтового сервиса Mock SMTP не должны блокировать моментальное отображение билета в браузере сразу после оплаты.

### 2.6 Распределение требований {#26-apportioning-of-requirements}

* **Релиз 1.0 (Текущая лабораторная работа — MVP):**
  * Требования приоритета **Must**: Регистрация/вход, каталог с фильтрацией, карточка события, корзина с бронированием, эмуляция оформления, генерация QR-билета, история заказов.
* **Релиз 1.1 (Следующие итерации):**
  * Требования приоритета **Should**: Скачивание билета в формате PDF (`REQ-FUNC-009`).
* **Релиз 2.0 (Перспективный скоуп):**
  * Требования приоритета **Could**: Применение промокодов (`REQ-FUNC-010`), электронный запрос возврата билета (`REQ-FUNC-011`), интерактивная схема рассадки зала (SVG).

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

Пользовательский интерфейс реализуется на базе библиотеки React и языка TypeScript с русскоязычной локализацией. Логическая структура интерфейса включает четыре ключевых экрана (согласно графическим макетам в `srs/img/`):
* **Экран каталога и поиска (`catalog.png`):** Верхняя панель со строкой поиска, выпадающие списки категорий, дат и диапазона цен. Сетка карточек событий с кнопками «Подробнее» и «В корзину».
* **Экран корзины (`cart.png`):** Таблица зарезервированных билетов с разделением по тарифам (VIP, Стандарт), счетчиками мест, таймером удержания брони (обратный отсчет 15 минут) и кнопкой «Оформить заказ».
* **Экран билета с QR-кодом (`ticket_qr.png`):** Карточка билета с контрастным QR-кодом размером не менее 256×256 px на белом фоне, текстовыми полями (название, дата, сектор, место, категория) и статусом валидности.
* **Экран истории покупок (`history.png`):** Хронологический список заказов с номерами квитанций, итоговыми суммами, метками статусов и кнопкой быстрого перехода к QR-билету.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

Приложение не обращается к специализированному аппаратному оборудованию напрямую. Экранное устройство клиента должно поддерживать отображение растровой графики в разрешении не менее 360×640 точек.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

Взаимодействие с бэкенд-сервисом билетов осуществляется по спецификации REST/JSON:
* `POST /api/v1/auth/login` — аутентификация пользователя с выдачей JWT-токена.
* `GET /api/v1/events` — получение выборки каталога с параметрами пагинации и фильтрации (`city`, `category`, `date_from`, `date_to`, `price_min`, `price_max`).
* `GET /api/v1/events/{id}` — получение подробной информации о событии и свободных квотах мест.
* `POST /api/v1/cart/reserve` — постановка билетов в резерв на 15 минут.
* `POST /api/v1/orders/checkout` — подтверждение покупки билетов из корзины.
* `GET /api/v1/orders/my` — получение перечня заказов авторизованного пользователя.
* `GET /api/v1/tickets/{id}/qr` — получение закодированных данных QR-кода.

### 3.2 Функциональные требования {#32-functional}

#### REQ-FUNC-001: Регистрация и аутентификация пользователей
* **ID:** REQ-FUNC-001
* **Title:** Учетные записи посетителей
* **Statement:** Система должна обеспечивать регистрацию новых пользователей по email и паролю, а также вход с сохранением сессии через JWT-токен. Без аутентификации пользователю доступны только просмотр каталога и детальная информация о событиях.
* **Rationale:** Разграничение доступа и привязка купленных билетов к конкретному физическому лицу.
* **Acceptance Criteria:** При успешном входе токен сохраняется в безопасном хранилище; при вводе неверного пароля выводится информативная ошибка.
* **Verification Method:** Test.
* **More Information:** Приоритет Must (таблица 3.4 отчета).

#### REQ-FUNC-002: Каталог мероприятий с пагинацией
* **ID:** REQ-FUNC-002
* **Title:** Отображение витрины событий
* **Statement:** Система должна выводить список доступных мероприятий в виде сетки карточек с указанием наименования, даты проведения, города, площадки, категории и стартовой цены.
* **Rationale:** Предоставление посетителю полного перечня культурно-массовых событий.
* **Acceptance Criteria:** Каталог поддерживает постраничную загрузку по 12 карточек на страницу.
* **Verification Method:** Test.
* **More Information:** Приоритет Must.

#### REQ-FUNC-003: Фильтрация и поиск мероприятий
* **ID:** REQ-FUNC-003
* **Title:** Поиск и выборка событий
* **Statement:** Система должна выполнять фильтрацию списка мероприятий по выбранному городу, диапазону дат, жанровой категории, диапазону стоимости и типу доступных мест (Стандарт/VIP), а также поддерживать регистронезависимый текстовый поиск по названию события.
* **Rationale:** Обеспечение нахождения билета менее чем за 3 минуты (бизнес-цель BG-2).
* **Acceptance Criteria:** Изменение параметров фильтра перестраивает витрину без полной перезагрузки страницы; присутствует кнопка «Сбросить все фильтры».
* **Verification Method:** Test.
* **More Information:** Приоритет Must.

#### REQ-FUNC-004: Карточка мероприятия
* **ID:** REQ-FUNC-004
* **Title:** Детализация события и квоты
* **Statement:** Система должна отображать расширенную страницу события с подробным описанием, адресом места проведения, типами билетов («VIP», «Стандарт»), их ценами и количеством оставшихся свободных мест.
* **Rationale:** Информирование посетителя перед принятием решения о бронировании.
* **Acceptance Criteria:** Если свободные места по тарифу отсутствуют, кнопка добавления блокируется с меткой «Билеты проданы».
* **Verification Method:** Test.
* **More Information:** Приоритет Must.

#### REQ-FUNC-005: Корзина и временное удержание брони
* **ID:** REQ-FUNC-005
* **Title:** Управление корзиной и резервом
* **Statement:** Система должна предоставлять интерфейс корзины с возможностью изменения количества билетов, удаления позиций, отображением общей стоимости заказа и запуском таймера временной блокировки выбранных мест на 15 минут.
* **Rationale:** Исключение конфликтов параллельной покупки одного места несколькими пользователями (риск R-1).
* **Acceptance Criteria:** В корзине визуализируется обратный отсчет времени; по истечении 15 минут бронь аннулируется на сервере, корзина очищается, пользователю выводится сообщение об истечении времени брони.
* **Verification Method:** Test.
* **More Information:** Приоритет Must.

#### REQ-FUNC-006: Оформление заказа и эмуляция оплаты
* **ID:** REQ-FUNC-006
* **Title:** Оформление покупки билетов
* **Statement:** Система должна выполнять подтверждение заказа с имитацией успешного проведения платежа, после чего заказ фиксируется на сервере, а билеты немедленно отображаются в разделе «Мои билеты».
* **Rationale:** Фиксация финансовой транзакции и перевод билета в активное состояние (бизнес-цель BG-1).
* **Acceptance Criteria:** При успешном подтверждении корзина очищается, пользователь перенаправляется на экран оформленного билета.
* **Verification Method:** Demonstration.
* **More Information:** Приоритет Must.

#### REQ-FUNC-007: Экран билета с визуализацией QR-кода
* **ID:** REQ-FUNC-007
* **Title:** Формирование электронного QR-билета
* **Statement:** Система должна отображать электронный билет с контрастным QR-кодом, содержащим зашифрованный верификационный токен, а также метаданные: дату, время начала, место, категорию билета («VIP» / «Стандарт») и текущий статус («Действителен»).
* **Rationale:** Обеспечение прохода через систему оптического контроля доступа турникетов (бизнес-цель BG-4, компонент № 4).
* **Acceptance Criteria:** QR-код генерируется на белом фоне с разрешением не менее 256×256 px; открытие билета занимает не более 2 действий из истории заказов.
* **Verification Method:** Demonstration.
* **More Information:** Приоритет Must.

#### REQ-FUNC-008: История покупок
* **ID:** REQ-FUNC-008
* **Title:** Реестр совершенных заказов
* **Statement:** Система должна отображать список всех оформленных пользователем заказов с датой операции, составом билетов, итоговой суммой, текущим статусом («Оплачен», «Использован», «Возвращён») и кнопкой прямого перехода к просмотру QR-кода билета.
* **Rationale:** Хранение билетов и оперативный доступ к ним в день мероприятия (бизнес-цель BG-4).
* **Acceptance Criteria:** Авторизованный посетитель видит исключительно свои заказы; клик по заказу открывает экран соответствующего билета.
* **Verification Method:** Test.
* **More Information:** Приоритет Must.

#### REQ-FUNC-009: Выгрузка билета в формате PDF
* **ID:** REQ-FUNC-009
* **Title:** Локальное сохранение билета
* **Statement:** Система должна предоставлять кнопку генерации и скачивания билета с QR-кодом в виде файла формата PDF для возможности автономного предъявления.
* **Rationale:** Резервный способ предъявления билета при отсутствии интернет-соединения у входа на площадку.
* **Acceptance Criteria:** PDF-документ содержит читаемый векторный или растровый QR-код и текстовое описание заказа.
* **Verification Method:** Test.
* **More Information:** Приоритет Should (отложено на релиз 1.1).

#### REQ-FUNC-010: Применение промокодов
* **ID:** REQ-FUNC-010
* **Title:** Скидочные промокоды
* **Statement:** Система должна позволять вводить промокод в корзине с автоматическим пересчетом итоговой стоимости заказа при валидности кода.
* **Rationale:** Маркетинговые кампании и программы лояльности.
* **Acceptance Criteria:** При вводе недействительного промокода выводится предупреждение, сумма не изменяется.
* **Verification Method:** Test.
* **More Information:** Приоритет Could (отложено на релиз 2.0).

#### REQ-FUNC-011: Инициализация возврата билета
* **ID:** REQ-FUNC-011
* **Title:** Возврат билетов из личного кабинета
* **Statement:** Система должна предоставлять пользователю возможность подать заявку на возврат билета из истории покупок с переводом статуса билета в состояние «Возвращён».
* **Rationale:** Снижение нагрузки на службу клиентской поддержки (бизнес-цель BG-3).
* **Acceptance Criteria:** Возврат возможен не позднее чем за 24 часа до даты начала события.
* **Verification Method:** Test.
* **More Information:** Приоритет Could (отложено на релиз 2.0).

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}
* **REQ-PERF-001 (Время отклика каталога):** Время полной загрузки и отрисовки страницы каталога не должно превышать 2,0 секунд при выборке до 1000 записей событий в базе данных.
* **REQ-PERF-002 (Отклик фильтрации):** Применение фильтров и текстового поиска должно производить обновление списка карточек не более чем за 1,0 секунду.
* **REQ-PERF-003 (Генерация QR):** Отрисовка QR-кода на экране клиента должна занимать не более 300 мс с момента открытия карточки билета.

#### 3.3.2 Безопасность {#332-security}
* **REQ-SEC-001 (Защита канала связи):** Весь трафик между клиентским веб-приложением и сервером должен передаваться исключительно по протоколу HTTPS с шифрованием TLS версии 1.3.
* **REQ-SEC-002 (Хранение учетных данных):** Клиентское приложение не должно сохранять открытые пароли; токены сессии должны храниться в защищенных куках (`HttpOnly`, `SameSite=Strict`).
* **REQ-SEC-003 (Изоляция данных):** Пользователь должен иметь программный доступ исключительно к своим заказам и билетам (защита от IDOR на стороне API).

#### 3.3.3 Надёжность {#333-reliability}
* **REQ-REL-001 (Сохранность билетов):** Купленный и оплаченный билет не должен теряться при сбоях сети или закрытии вкладки браузера: после успешной транзакции запись о билете сохраняется на сервере и отображается при повторном входе.
* **REQ-REL-002 (Обработка сетевых ошибок):** При обрыве связи клиентское приложение должно выполнять до 3 повторных запросов с экспоненциальной задержкой перед выводом диалогового окна ошибки.

#### 3.3.4 Доступность {#334-availability}
* **REQ-AVAIL-001 (Готовность сервиса):** Доступность клиентского веб-приложения должна составлять не менее 99.5% в режиме 24/7 (за исключением плановых технических регламентов).

#### 3.3.5 Наблюдаемость {#335-observability}
* **REQ-OBS-001 (Клиентское логирование):** Критические ошибки сценариев (ошибки парсинга, падения компонентов интерфейса) должны перехватываться с помощью React Error Boundary и регистрироваться в консоли разработчика с выводом дружелюбного экрана «Что-то пошло не так».

### 3.4 Соответствие стандартам {#34-compliance}

* **REQ-COMP-001 (Контракт API):** Программные интерфейсы взаимодействия клиента с серверной частью должны строго соответствовать спецификации OpenAPI 3.0.
* **REQ-COMP-002 (Персональные данные):** Обработка данных пользователей (email, ФИО) должна соответствовать нормам Закона РБ от 07.05.2021 № 99-З «О защите персональных данных».
* **REQ-COMP-003 (Доступность UI):** Контрастность текста, управляющих кнопок и QR-кода должна удовлетворять стандарту WCAG 2.1 (уровень AA).

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}
Клиентское приложение компилируется в набор статических файлов (HTML, JS, CSS, assets) и не требует развертывания исполняемых сред на компьютере конечного пользователя.

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}
Сборка проекта выполняется с использованием Vite/Node.js. Автоматизированный процесс сборки и запуска линтеров настраивается через пайплайн GitHub Actions.

#### 3.5.3 Распределение {#353-distribution}
Скомпилированное веб-приложение размещается на веб-сервере Nginx с возможностью раздачи через распределенные сети CDN для снижения задержки доставки контента.

#### 3.5.4 Сопровождаемость {#354-maintainability}
* **REQ-MAINT-001:** Архитектура фронтенда должна следовать четкому разделению на слой представления (React-компоненты), слой управления состоянием и изолированный слой сервисов API-клиента.
* Покрытие модульными тестами логики корзины, таймера и валидаторов должно составлять не менее 70%.

#### 3.5.5 Повторное использование {#355-reusability}
Модуль отрисовки QR-кода выделяется в автономный компонент для возможности повторного включения в смежные подсистемы (например, в веб-интерфейс мобильного сканера билетов).

#### 3.5.6 Переносимость {#356-portability}
Приложение должно функционировать без различий в верстке и поведении в настольных ОС (Windows 10/11, macOS, Linux) и мобильных платформах (Android, iOS).

#### 3.5.7 Стоимость {#357-cost}
Проект реализуется на базе свободного стека ПО с открытым исходным кодом (React, TypeScript, Lucide Icons, Vite) без лицензионных затрат на покупку проприетарных библиотек.

#### 3.5.8 Сроки {#358-deadline}
Разработка документации требований и интерфейсных прототипов завершается в рамках сроков сдачи лабораторной работы № 3 по календарному графику учебного процесса БГУИР.

#### 3.5.9 Доказательство концепции {#359-proof-of-concept}
Осуществимость считывания сгенерированного динамического QR-кода экраном смартфона подтверждена в ходе стендового тестирования с эмуляцией сканера (компонент № 4).

#### 3.5.10 Управление изменениями {#3510-change-management}
Все изменения спецификации и сопутствующих моделей вносятся в ветку `lab3-requirements` и утверждаются посредством механизма pull-request с участием напарника (Заказчика) и преподавателя.

### 3.6 ИИ/МО {#36-aiml}

В текущей версии 1.0 клиентского приложения применение моделей искусственного интеллекта и машинного обучения не предусмотрено. Подразделы 3.6.1–3.6.6 исключены из проектного скоупа.
